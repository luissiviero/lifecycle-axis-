# Pairing the SDLC playbook with the Open Knowledge Format (OKF)

> Source: Google Cloud, *Introducing the Open Knowledge Format*, 12 Jun 2026. OKF v0.1 is a directory of Markdown files
> with YAML front matter. The only required field is `type`; conventional fields are `title`, `description`, `resource`,
> `tags`, `timestamp`. File path is identity, Markdown links form the graph, `index.md` gives progressive disclosure,
> `log.md` gives chronological history.

## Opinion: yes, pair them, but at one specific seam

The two ideas are complementary because they solve different problems with the same material.

- The playbook is a **process** whose state lives in Markdown artifacts with front matter. It is Claude-shaped at the
  enforcement layer (hooks, skills, `CLAUDE.md`, managed settings) and model-neutral at the artifact layer.
- OKF is a **knowledge format**, deliberately not a platform, so that any producer (a human, a pipeline, Claude, Gemini)
  and any consumer (an agent, a catalog, a viewer) can share the same files without translation.

For a team that runs both Claude and Gemini, the risk is two divergent memories: a `CLAUDE.md` plus Claude skills on one
side, a `GEMINI.md` on the other, each drifting. OKF is the right fix for exactly that layer. It is the wrong tool for
the enforcement layer, which stays in hooks (Claude), CI and branch protection (any model).

**Where to pair**
1. **The artifact chain becomes an OKF bundle.** `intent.md`, `spec.md`, `plan.md`, `incident.md` already carry front
   matter. Adding `type: sdlc/intent` (etc.), `title`, `description`, `resource`, `tags`, `timestamp` costs nothing
   (this repo's templates already include them) and makes `work/` consumable by Google's Knowledge Catalog, an OKF
   visualizer, or a Gemini agent with no adapter. The playbook's audit trail becomes a browsable knowledge graph:
   intent → spec → plan → PR → incident → next intent, linked by ordinary Markdown links.
2. **A model-neutral knowledge bundle for institutional knowledge.** `knowledge/` holds concepts (services, tables,
   metrics definitions, runbooks, architecture decisions, lessons) as OKF documents. `CLAUDE.md` and `GEMINI.md` stay
   one page each and point into it, which is also how the playbook wants `CLAUDE.md` kept short. Skills for Claude and
   the equivalent instructions for Gemini cite the same concept files, so a policy has one source of truth.
3. **`log.md` as the machine-readable ledger of gate decisions.** Each `work/<slug>/log.md` appends stage transitions
   and approvals (who, when, what SHA). That is the playbook's audit trail in a form a catalog can index and a script
   can check, and it fills a real gap: today approvals live only in git history.
4. **Lessons and post-mortems as OKF concepts.** The Claude Tag play writes lessons to a version-controlled file; as
   `type: lesson` documents linked to their incident they are discoverable by any agent, not only Claude.

**Where not to pair**
- Do not represent hooks, gates, or permissions in OKF. They are enforcement, not knowledge, and each runtime has its own.
- Do not make OKF conformance a merge gate before v1.0 of the spec. Run the conformance check as a warning and promote
  it to a failing check once the format is stable and something actually consumes the bundle.
- Do not duplicate: `CLAUDE.md` must not restate what `knowledge/` holds. It links.

## What this adds to the implementation plan

| Item | Change | Enforcement |
|---|---|---|
| OKF front matter on all artifacts | done in templates: `type`, `title`, `description`, `resource`, `tags`, `timestamp`; SDLC extensions (`status`, `approved-by`, `kind`, `record`) are allowed by OKF's minimal-opinion rule | chain check already reads `status`/`approved-by` |
| `work/index.md` and `work/<slug>/index.md` | generated by a script on commit; progressive disclosure for agents | CI regenerates and fails on drift |
| `work/<slug>/log.md` | appended by `/sdlc-*` skills and by humans at approval | chain check verifies each `status: approved` has a matching log entry with a name |
| `knowledge/` bundle | `index.md`, `services/`, `metrics/`, `runbooks/`, `decisions/`, `lessons/`; migrate `docs/sdlc/lessons.md` there | `scripts/check_okf.py`: every doc has `type`; links resolve; timestamps RFC3339 (warning first) |
| `GEMINI.md` (and `AGENTS.md`) | one page, same eight hard rules, pointing at the same `knowledge/` and `work/` | reviewed like `CLAUDE.md`; both files' rule sections generated from one source to prevent drift |
| Gemini enforcement parity | Gemini has no equivalent of Claude hooks in this repo; the deterministic gates that must hold for both live in CI (`sdlc-gate`) and branch protection, not in hooks | CI is model-agnostic by construction |
| Producers | optional: enrichment step that drafts OKF concept docs for new services/tables from the codebase, reviewed like code | PR review gate |

Open questions for the plan: which Gemini surface is in use (Gemini CLI, Antigravity, Vertex agents), whether a Knowledge
Catalog or any OKF consumer exists today, and whether `knowledge/` lives in each product repo or in one shared bundle.
