# Step review, 2026-09-10

**Status: first draft, for the owner's revision.** Nothing in this document changes the repository by being
written. Every row that says *change*, *fix*, *build* or *drop* is a proposal; the owner accepts, edits or
rejects it, and what survives becomes work items through the chain, as `docs/sdlc/spikes/build-stage-from-claude-agents.md:23`
already requires of any proposal.

## 0. How to read this

**What a step is.** One action the kit prescribes for a human, an agent, a hook or CI: in the life of one work
item (lens A, rows 1–110), in adopting the kit into another repository (lens B, rows 111–139), or in the Maintain
loop (rows 140–164). The rows are the 164 steps in [`evidence/steps.md`](evidence/steps.md), in the same order,
with the same numbers, each with its defining file and line there. That inventory was produced mechanically from
every skill, hook, workflow, template, script docstring, rule fragment, decision and work item, so a step that
is missing here is a step missing from that file, which is checkable.

**Where the answers come from.** Column 3 names the interview questions (Q1–Q30, listed in Appendix A) that the
step answers, and gives the answer the repository gives *today*, not the owner's wish. The full answers with
citations are in [`evidence/answers.md`](evidence/answers.md). Two more reports feed columns 4–6:
[`evidence/drift.md`](evidence/drift.md) (the kit's own checks run on `main`, docs against code, dead references,
unbuilt declarations, the bookkeeping share of recent merges) and [`evidence/history.md`](evidence/history.md)
(how the plan changed day by day, the share of the repo each founding idea occupies, every unmerged branch).

**Column 4 vocabulary.**

| Word | Meaning |
|---|---|
| keep | the step stands; nothing to do |
| keep (note) | the step stands; the note names a small doc or wording fix |
| change | the step stays but its shape, actor or enforcement changes |
| fix | the step is broken today; evidence in column 5 |
| build | the step is declared in a document and has no code; build it or delete the claim |
| drop | remove the step, or remove the claim that the kit performs it |
| merge → n | fold this step into row n |

**The design stance behind the assessments.** The rows lean on seven positions, stated once here so column 5 can
cite them by letter instead of repeating them. Each is a proposal like any row.

- **A. One source.** A rule, a command line or a contract string is written in one file and rendered or linked
  everywhere else. The review found the verify line in four places, the tap inputs in five skills, the lesson
  destination in three, and the required-checks list disagreeing with itself in three (Appendix B).
- **B. The plan is on disk and in front of the agent.** The active plan is re-injected after compaction, progress
  is ticked in the plan file, and a path outside the plan's file list is refused at the edit, not at the pull
  request. This is pull request 67's design, and the repository's own diagnosis of the failure the owner quoted.
- **C. One human act per item, at the start.** For low-risk items the default is delegated under a standing grant;
  the owner's remaining acts are the grant policy, the merge click on control-plane diffs, and answering
  questions. Supervised mode is what the owner asks for, not the default. Retirement and the pointer move stop
  being human acts.
- **D. Bookkeeping is generated by CI, never by hand and never in a pull request diff.** The last eight merges
  were 43% regenerated indexes and ledgers and 27% chain paperwork; four of eight touched no code. Three of the
  fourteen lessons and one red `main` came from index regeneration alone.
- **E. Models are routed by a table, recorded by a script, and measured before they are optimised.** A
  role-to-model table in the control plane, a `model:` pin in every agent file, the writer and reviewer models
  written into the ledger by the tool that makes the gate, and one cost line per item (tool calls, turns, wall
  time, Actions minutes) as the stand-in for the cost ledger two decisions are waiting on.
- **F. Nothing without a consumer is documented as running.** Scans, on-call, the 5xx band, the 3σ routes, the
  deploy environment, the Gemini and Antigravity surfaces and the plugin channel get one status word each in one
  list, and the README stops presenting them as plays the repo performs.
- **G. The kit is proven on a second repository, not on itself.** Every one of the twenty work items is about the
  kit. "Done" for v1 is one item shipped in another repo under delegated mode with one tap.

**Five findings that change the picture**, before the rows:

1. The queue's advance has never landed on `main`: the push after every delegated merge is rejected as
   non-fast-forward and swallowed as a note (row 100). The Actions API confirms it: of the last hundred
   `delegated-merge` runs, 8 succeeded, 38 failed and 54 were skipped, and `main` has no advance commit.
2. Retiring a delegated item is impossible as the rules stand, so 19 of 20 items are still open (row 104).
3. The reviewer subagents are documented three times as read-only and all four carry unbounded `Bash`
   (row 60, row 78). The agent's own instruction files, `REVIEW.md` and `CODEOWNERS` are outside
   `PROTECTED_PATHS` (row 48).
4. `scripts/verify.sh` ends `VERIFY: FAIL` on a clean `main` in any environment with a GitHub token and no
   `gh` binary, this session's included (row 65).
5. The decision that CI is informational rests on the repo being private on the Free plan; the repo went public
   on 2026-09-09 and the decision carries no amendment, so branch protection is now available and absent (row 96).
