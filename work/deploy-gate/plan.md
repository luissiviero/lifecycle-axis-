## Risks
- Risk: `fm_value`, `approver_has_role` and `log_decision` in `_lib.sh` come from the `control-plane-visibility` item and `approvers.py --has-role` from the `front-matter` item; if either merges in a different shape, this item's code and tests drift → mitigation: step 1 verifies them before any edit; a difference is recorded in the Deviations log in the same commit and the plan's file list is amended.
- Risk: the hook is live in this session; a broken `production-gate.sh` blocks every Bash call → mitigation: `bash -n` after the single edit, tests from a second shell before the next tool call.
- Risk: the word pair over-asks on harmless commands → mitigation: the five allow strings are pinned by test; a false positive is one prompt, never a block in an attended session.
- Risk: after the workflow change every CI deploy refuses until a human stores `RELEASE_APPROVAL` as an Environment secret or commits an authorization file → this is the intended fail-closed state; the runbook says how to store it.
- What this could break: nothing deployed (`deploy.sh` echoes); `deploy.yml` runs fail until authorized; no verdict on a command that passes today changes except the routes named in spec R-2.
- Options considered and not taken: dropping the env route (adopters with real Environment reviewers need it); one regex instead of `is_deploy()` (two independent matches over one command); calling `python3` from the hook (Windows Store stub, latency); writing an authorization file in the real repo for the eval (control-plane write from an agent).
