# Revision 1: the guard asks which call site it is serving, and it fails closed

## Proposal
Four changes to `spec.md`, the first two clearing the trigger and the last two from the security pass:

1. **R-1's middle condition** becomes "the caller did not ask for the self-check", spelled as the
   literal `a.base != "HEAD"`, instead of "`--base` resolves to a different commit than `HEAD`". The
   discriminator the requirement actually needs is call-site identity, not commit identity: `verify.sh`
   asks for the self-check by passing literally `--base HEAD` (`.sdlc/config.env:25`), and every other
   caller passes `origin/<ref>` (`sdlc-gate.yml:41`, `deploy.yml:49`, and the argparse default at
   `check_artifact_chain.py:476`). R-2's own prose already framed the exemption this way — "its diff is
   empty by construction" — so the rev comparison was a mechanism invented in the Design section that
   the requirements never asked for.
2. **The `_rev` hoist and decision D2 are dropped.** With the rev comparison gone from the guard,
   nothing outside `if active_now:` needs it, so `check_artifact_chain.py:570-571` is left untouched.
   This shrinks the diff, removes plan step 2 entirely, and retires the risk that hoisting reopens the
   stale-pointer behaviour `work/retire-active-pointer` R-2 pinned.
3. **A failed `git status` refuses instead of assuming a clean tree.** The security pass is right that
   the signed text fails open in the one place this item exists to close: if the check cannot determine
   whether the tree is dirty, it cannot claim to have examined it. The refusal takes the same shape as
   the unknown-base-ref case at `:527-535`, which already treats "git cannot answer" as `CHAIN: FAIL`.
4. **Two documented additions, no behaviour change.** A gotcha recording that the guard's literal
   predicate and the `_rev`-based `self_check` at `:570-571` answer deliberately different questions, so
   a later "cleanup" cannot unify them and reintroduce the inertness this revision fixes; and an entry
   under Areas of concern that a future caller spelling the self-check differently (`--base @`, a sha,
   `refs/heads/main`) would bypass the guard silently. All three callers were enumerated and none does.

Also taken, as a nit rather than a requirement change: the porcelain sample becomes rename-aware.
`git status --porcelain` renders a rename as `R  old.txt -> new.txt` (verified), which column-4 parsing
would print as one combined descriptor rather than a path.

Not proposed: firing whenever the tree is dirty regardless of the diff. Both reviewers and the signed
spec agree that reaches into "Not doing" (`spec.md:135`) and would fire during ordinary iterative work.

## Reviewer: plan-reviewer (sonnet)
Reproduced the trigger independently in a scratch repository rather than trusting the writer's
transcript, and confirmed the base and HEAD resolve to the identical sha in the recorded scenario, so
the signed condition is inert in its only motivating case. Verified every caller of the script, not only
the ones the spec's gotcha G-6 claims: `.sdlc/config.env:25`, `sdlc-gate.yml:41`, `deploy.yml:49`, the
argparse default at `:476`, and every direct importer including `delegated_merge.py:48`, which never
touches `--base`. Found that R-2's text already frames the exemption in terms of the literal flag rather
than any rev comparison, so the mechanism being removed was never required by the requirements. Weighed
the two alternatives put to it and rejected both: firing on any dirty tree reaches into the spec's own
"Not doing", and keeping the rev check alongside a literal exemption is redundant, because condition (a)
already makes rev-equality near-tautological in the bad case, which is why it was inert. Judged the
change smaller than the trigger requires rather than larger, since plan step 2 disappears and `:570-571`
stays untouched; confirmed no test names `_rev` or the lambda, so nothing is orphaned. Listed eleven
specific spec and plan lines that go stale, and asked that "Options considered and not taken" record the
inert rev condition so a later reader does not repeat it. Judged the residual fragility of a literal
comparison against a future differently-spelled caller worth one line under Areas of concern, not a
blocker, because the caller set is closed and enumerated.
verdict: revise

## Reviewer: security-reviewer (sonnet)
Applied security-standards rule by rule: rules 1, 2, 4, 5 and 6 are n/a with reasons given (no secret,
no auth path, no new field, no dependency, no path under `RELEASE_GATED_PATHS`), and rules 3, 7 and 8
apply and are met. Reproduced the trigger before assessing it. Worked the bypass question in both
directions and found the proposal strengthens rather than weakens the guarantee: the literal `"HEAD"`
cannot be spoofed, because a self-diff is genuinely empty whenever the base is literally `HEAD`, and
neither workflow caller can ever produce that string, both being files a pull request author cannot
edit. Concluded that `knowledge/lessons/one-path-spelling-in-guards.md` argues for the proposal rather
than against it: resolving refs to commits is over-normalisation that erases the distinction the guard
needs, and the resulting silent allow is the worst failure a guard can have. Verified the untrusted-path
handling directly, confirming `repr` escapes ESC, newline and quote, and that git pre-escapes control
characters in porcelain output before Python sees them. Raised one Important finding beyond the
proposal: a failed `git status` treated as "not dirty" fails open in exactly the place this item exists
to close, and is inconsistent with the fail-closed precedent at `:527-535`; it asked for that to be
fixed in this same revision. Raised two nits: the porcelain parsing is not rename-aware, and the
revision should say why the two self-check predicates are intentionally different, so a later edit does
not unify them and reintroduce the bug. All three are taken in the proposal above.
verdict: revise
