# Revision 1: `approved-by` on a retired artifact is skipped only where the ledger shows a signature

## Proposal
The smallest change to `spec.md` that clears the trigger and keeps the intent's observables:

1. **R-1 row.** From "the chain check no longer validates `approved-by` against `.sdlc/approvers.yaml`"
   to: on a `superseded` artifact the ledger shows signed under a grant (a `-> delegated` line for it
   whose actor is the handle in `approved-by`, the line `sign.py` writes) the check does not validate
   `approved-by`; on one a human approved (no such line) the approver check stays as it is. Everything
   else in the row (the retirer read from the `-> superseded` line, the author or trailer of the
   retiring commit, the acceptance test) is unchanged. The actor binding is the security pass's
   finding on the first form of this proposal, which accepted any `-> delegated` line or a retiring
   line from `delegated`: a stray line by another handle must switch nothing off.
2. **D1.** One sentence added: the approver list is still asked about `approved-by` when the ledger
   shows no signature for the artifact, because a human-approved artifact's approver was a valid handle
   and a bot handle there is a malformed record, which the pre-existing case pins.

Why this is the smallest change: the intent's three observables all still hold (the agent-signed tree
passes, the agent-actored retiring line fails naming the line, nothing an agent can do widens); the
signature is read from the ledger the retirer and the check already read, not from `approved-by`; and
the narrowing is strictly stricter than the approved wording, so no case that passed under the approved
R-1 fails under this one except the one the trigger names, which must fail. The alternative, editing the
pre-existing case, breaks the intent's Must directly.

What else goes stale: nothing in the plan's file list or order. The R-2 acceptance test is unchanged
because `signed` is read from the artifact's `-> delegated` line (any such line in the ledger whose actor
is the handle in `approved-by`), not from the retiring line, so on a signed artifact an agent-actored or
missing retiring line leaves the approver check off and is reported once, as the ledger fault it is. The
R-1 row gains the binding's two pins in its acceptance column, and D1 gains the one new consequence: a
retired signed artifact is valid only while that `-> delegated` line is still in its ledger, so the
ledger's append-only rule is load-bearing for retirement validity, and a truncated ledger fails closed
with a human fix. The spec's gotchas missed the trigger's case although the spec read it while it was
written (plan deviation 3 says so).

On a supervised item there is no `sign.py --revision`: the record is committed, the two reviewer sections
below are the consensus, and the owner's acceptance is a ledger line in their own hand, asked for on the
pull request.

## Reviewer: security-reviewer (claude-opus-5)

**Does the trigger block the plan as written?** Yes, and the plan cannot absorb it. R-1 as approved says the check "does not validate `approved-by` against `.sdlc/approvers.yaml`" on a `superseded` artifact, without a condition. `scripts/test_check_artifact_chain.py:302-312` (`test_superseded_with_an_invalid_approver_fails`) builds a human-approved `plan.md` relabelled `approved-by: claude[bot]` with a valid human `approved -> superseded` line and asserts exit 1 and `approved-by 'claude[bot]' is not valid`; under the approved wording that tree passes. The intent's Must ("keep every existing chain-check case green unmodified") and that wording cannot both hold, and the plan closes the other exit: its file list gives `scripts/test_check_artifact_chain.py` additions only, and step 2's Verifiable clause requires every pre-existing case in the module green (spec R-4 pins the same with `--numstat`). So the spec row has to move, not the plan and not the case. A revision record rather than a deviation line is the right instrument: this changes what an approved spec row means, not how the plan reaches it.

**Is the proposal the smallest change, and what does it open or close?** Yes: one clause in R-1, one sentence in D1, no change to the retirer rule, the trailer route, the acceptance tests or R-2 to R-13. The narrowing is strictly stricter than the approved wording, so the only tree whose verdict changes is the trigger's.

On the security question I looked at the actor binding specifically, because the first form of this proposal (any `-> delegated` line for the artifact, or a retiring line from `delegated`) made an agent-writable file the switch. `work/<slug>/log.md` is a file agents append to routinely, so that form let one fabricated line turn the approver check off on a retired artifact a human approved. Measured on the pre-binding code, one fabricated `| plan.md | approved -> delegated | claude |` line flipped the fixture above from `CHAIN: FAIL` (`approved-by 'claude[bot]' is not valid`) to `CHAIN: PASS`; with the binding in the working tree (`scripts/check_artifact_chain.py:767-772`) the same tree is `CHAIN: FAIL` again. The binding is not an arbitrary tightening: it is the invariant `scripts/sign.py` already maintains, writing `approved-by: handle` (`:228`) and the ledger line's `actor=handle` (`:232-233`) from one variable in one run, so every real signature satisfies it, including a re-signature (`delegated -> delegated`) and a handle that changes between sessions, since the check asks `any()` over the whole ledger. What it closes: the approver list keeps its say on every human-approved retired artifact, so a retroactive rewrite of `approved-by` there stays a CI failure and not only a hook refusal (`.claude/hooks/protect-approvals.sh:51`). What it opens: nothing an agent can reach on its own — to reach the skip the agent's own handle must already be in `approved-by`, which only `sign.py` under a grant, or a human, writes; where `approved-by` holds a human handle the skip is a no-op, because `av.is_valid` would have passed anyway. The one real cost is fail-closed and is the clause the proposal drops: a signed artifact whose ledger has no `-> delegated` line for it (a hand-written or truncated ledger) is now reported `approved-by '<agent>' is not valid`. That is a true record fault with a human fix (append the signature line the signature actually made), and keeping the "retiring line from `delegated`" alternative would reinstate an unbound, agent-writable trigger, so dropping it is correct. I checked the production case the spec's `## Data and migrations` paragraph promises: `work/approve-tap-regenerates-index/log.md:17-18` carries `| spec.md | in-review -> delegated | claude |` against `approved-by: claude`, and `log_ledger.normalize("claude") == av.normalize("claude")` is True, so the item this work exists to turn green still turns green under the binding. Had the binding not matched the handle `sign.py` actually writes, this amendment would have re-broken it.

**What else breaks or goes stale.** Nothing in the plan's file list, order, risks, rollback or proof; the four modules run 225 green in the working tree, with `scripts/test_check_artifact_chain.py` still additions only. R-2's "exactly one FAIL line" holds, because a signed artifact with an agent-actored retiring line still produces the ledger fault alone. Three small debts should land with the record rather than after it: R-1's acceptance-test cell should name `test_a_delegated_line_by_another_handle_switches_nothing_off` so the row keeps a test per requirement, and that case should be recorded as seen red against the pre-binding code (`knowledge/lessons/a-verifiable-command-fails-before-the-change.md`; the before/after measurement above is that evidence); the `## Data and migrations` sentence now depends on the binding and should say so, since it reads today as if any agent-signed retired item goes green rather than the ones whose `-> delegated` actor is the handle in `approved-by`; and the plan's deviations log, which already carries deviation 3, should point at `revisions/1.md` so the ledger, the plan and this record agree on one story. None of these blocks the amendment.

verdict: revise
