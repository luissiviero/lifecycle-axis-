## Risks
- Risk: `test_adopt.py` runs seven scenarios concurrently and each full adopt is ~1 s on Linux, ~20 s on the owner's Windows PC; five more scenarios add to that → mitigation: the new scenarios reuse `run_adopt`, the git-based one is the only one that commits; `SDLC_ADOPT_JOBS` still bounds parallelism.
- Risk: the approval scenario runs the copied approval script in a subprocess; in this session `CLAUDECODE` is set and the script refuses → mitigation: the scenario builds its environment without `CLAUDECODE` (`os.environ` copy with the key removed), which is exactly the adopter's shell; the kit's `protect-approvals.sh` judges Bash command text, not a Python subprocess's argv.
- Risk: the settings merge changes an adopter's JSON formatting → mitigation: rewritten only when something was added, two-space indent, keys in the adopter's order; reported.
- Risk: the differs-from-kit line is noisy for files `adopt.sh` rewrites → mitigation: `REWRITTEN` excludes them.
- What this could break: nothing in this repo's runtime; `adopt.sh` is not run by any hook, check or workflow here. The kit's own `work/_example` is untouched.
- Options considered and not taken: a chain-check exemption for the install commit (spec D1); copying the kit's knowledge bundle (D6); a `never-approve` entry for the placeholder (C1); PyYAML or `jq` for the merge (stdlib `json` is already required by the renderers).
