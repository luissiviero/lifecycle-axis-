## Design
### Architecture / data flow
Nothing new flows and no service is added. Four workflow files gain guards and concurrency groups, one reader inside the merge script loses a class of input, one condition inside it gains a verdict, and one pure function is added to a metrics script.

**The gate's decision, in order.** GitHub delivers a `pull_request` event; the `concurrency:` block (R-3) decides whether an earlier run of the same pull request is cancelled or queued; the job's `if:` (R-1, R-2) decides whether the job starts at all. A job that does not start produces a run whose conclusion is `skipped`. That conclusion is the seam between the workflow half and the script half of this item: R-9 exists because R-1 creates skipped runs on head shas that later go ready.

**Why a skipped run is not evidence.** A `pull_request` run concludes `skipped` only when every job's `if:` evaluated false. After R-1 the only such condition on `sdlc-gate` is "the head was a draft" or "a Bot edited the body", and on `pr-review` it is the draft skip already at `:41-42`. Neither says anything about the code at that sha. `_pr_runs` (`scripts/delegated_merge.py:243-250`) is the single reader behind all three run-based conditions, so one clause there fixes `check_required_runs`, `check_review` and `check_cool_off` together. `check_check_runs` needs nothing: `OK_CHECK_CONCLUSIONS` (`:78`) already accepts `skipped`.

**Why `cancelled` is still refused.** R-3 binds `cancel-in-progress` to `synchronize`, so a cancelled run belongs to a sha that a later push replaced; it can never be the head sha being judged. Keeping the refusal costs nothing and keeps the condition fail-closed against a case the design does not produce.

**Where the not-delegated verdict lives, and why not where the guide put it.** The implementation guide proposed a new `delegation` condition recorded after `event` and before `pull-request`. That is not implementable: the work-item slug comes from the pull request body and the base ref from the pull request (`scripts/delegated_merge.py:777-800`), and both are inputs to reading the intent. The mode is already read exactly once, in `check_grant_front_matter` (`:386-411`), from the base branch through the GitHub API (`:806-809`), never from the local checkout — the module docstring at `:7-10` explains why the base must be the source of truth. So the change is a reorder inside that function and one entry in `Run._code`, not a new condition. The verdict name is new; the condition name stays `grant`, which keeps every existing line of the printed output stable.

**The measure.** `scripts/github_metrics.py` currently dispatches on metric name in two places, and both are two-way rather than exhaustive: `_api_path` (`:83-92`) returns the pulls path for anything that is not `ci_test_failure_rate`, and `main` (`:176-179`) calls `pr_cycle_series` for anything that is not `ci_test_failure_rate`. A third metric added without restructuring would silently produce a pull-request series under an Actions name. Both become explicit dispatch, so an unknown metric is a visible error rather than a wrong number.

## Decisions (ADR-style: context → decision → consequences)
- D1: **The not-delegated verdict lives in `check_grant_front_matter`, not in a new condition.** Context: the implementation guide placed it after the `event` condition, but the slug and base ref that identify the intent are only known after the pull-request condition resolves (`:777-800`), and the mode is already read once, from the base branch through the API (`:806-809`). Decision: reorder the mode test above the status test inside that function and add the verdict there. Consequences: no new API call, no new condition line in the output, and the condition keeps its name `grant`. A supervised item whose intent is not yet approved now also reports `not-delegated` rather than a status refusal, which is the more accurate statement: mode, not status, is what makes the run someone's business.
- D2: **Only `skipped` is dropped from a pull request's runs; `cancelled` still refuses.** Context: the guide proposed a superseded-run rule comparing run ids so that a `skipped` or `cancelled` run is ignored when a later run of the same workflow on the same sha succeeded. Decision: the simpler rule, one clause in `_pr_runs`. Consequences: about half the tests, no id arithmetic, and the three run-based conditions are fixed by one edit instead of two call-site edits. The case the id comparison covered and this does not — a `cancelled` run on the judged head sha — cannot arise once R-3 binds cancellation to `synchronize`. If that binding is ever loosened, this decision must be revisited, and the note in the rollback table says so.
- D3: **The minutes series filters on `event`, not on `head_branch`.** Context: the guide counted runs whose `head_branch` is not the default branch and claimed that included the merge wake. Decision: count every run whose `event` is neither `schedule` nor `workflow_dispatch`. Consequences: the `delegated-merge` wakes, which the live API reports with `head_branch: main`, are counted where the guide would have dropped them; the nightlies stay excluded; the divisor remains the distinct non-default branches in the day, and a day with billable runs and no such branch is omitted rather than dividing by zero.
- D4: **The gate keeps its `edited` trigger and skips Bot senders.** Context: `edited` cost a full duplicate gate run per bot body edit. Decision: keep the trigger, guard on the sender type. Consequences: a human fixing the `Work-Item:` line still gets a run, which is the reason `edited` was added; Sourcery, the observed cause, is uninstalled, so the guard is now insurance rather than a fix.
- D5: **Drafts get no gate at all, rather than a gate without the review.** Context: the owner's answer to the intent's first question. Decision: skip. Consequences: the runner's Linux signal arrives one round later, at ready. Pull request 61 recorded seven suites red on the owner's Windows machine and green on the runner; the reverse case is what this defers, and the ready gate catches it before any merge.
